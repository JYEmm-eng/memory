### 📊 최종 보고: LTV:CAC 데이터 로깅 및 확장 방안

#### 1. 현황 분석 (검증 결과 요약)
이전 검증 단계에서 확인된 핵심은 **UTM 파라미터가 DB에 정상적으로 매핑되는지**와 **데이터 흐름의 안정성**입니다. 이는 초기 LTV:CAC 측정의 기반이 됩니다.

*   **확인된 안정성:** UTM 데이터 수집 로직과 DB 스키마 간의 1차 연동은 논리적으로 안정됨을 확인했습니다.
*   **잠재적 확장 영역:** 현재는 주로 트랜잭션 레벨의 추적에 중점을 두었으나, 서비스 확장을 위해서는 사용자 행동(Behavioral Data) 및 외부 채널 기여도(Attribution Depth)를 더 깊이 로깅해야 합니다.

#### 2. 향후 데이터 로깅 방안 구체화 (확장 전략)
서비스 확장 단계에서 요구되는 데이터 로깅은 크게 **3단계**로 구조화하고, 각 단계에 필요한 로그 항목을 정의합니다.

**A. 레벨 1: 트랜잭션 및 기본 지표 (현재 유지/강화)**
*   **목표:** LTV/CAC의 기초 산출을 위한 핵심 데이터 확보.
*   **로깅 항목:** `user_id`, `session_id`, `acquisition_channel` (UTM 파라미터 기반), `transaction_value`, `timestamp`.
*   **안정성 요구사항:** 이 단계는 기존 시스템의 안정성을 100% 보장해야 합니다.

**B. 레벨 2: 사용자 행동 및 참여 지표 (Behavioral Data)**
*   **목표:** 사용자의 서비스 내 몰입도와 전환 과정에서의 병목 현상을 포착하여 '학습 경험' 데이터로 활용. (회사 목표와 직접 연결)
*   **로깅 항목:** 세션별 페이지 뷰 깊이, 특정 학습 패턴 반복 횟수, 콘텐츠 소비 시간(Engagement Time), 집중도 변화 지표(만약 프론트엔드에서 수집 가능하다면).
*   **확장 방안:** 기존 DB 스키마에 `user_activity` 테이블을 추가하고, 실시간 스트리밍 또는 배치 처리를 통해 데이터를 집계하는 파이프라인을 구축해야 합니다.

**C. 레벨 3: 외부 채널 및 마케팅 기여도 (Attribution Depth)**
*   **목표:** 어떤 마케팅 채널이 실제 학습 성과(LTV)에 가장 큰 영향을 미쳤는지 정량화.
*   **로깅 항목:** 광고 노출 시점의 상세 정보, 콘텐츠 유형별 전환율 매핑, 사용자 유입 경로의 복합 지표.
*   **확장 방안:** 외부 마케팅 API와 연동하여 UTM 데이터와 내부 행동 데이터를 교차 분석하는 **데이터 웨어하우스(DW)** 레이어를 구축해야 합니다.

#### 3. 기술적 로깅 아키텍처 제안 (엔지니어링 관점)
논리적 안정성을 확장 가능한 구조로 만들기 위해, 기존의 단순 트랜잭션 로그에서 벗어나 **이벤트 스트림 기반**으로 전환을 제안합니다.

1.  **Event Stream 도입:** 모든 사용자 상호작용(클릭, 뷰, 학습 완료 등)을 Kafka 또는 유사한 메시지 브로커를 통해 이벤트 스트림으로 발행하도록 시스템을 설계합니다.
2.  **Data Ingestion Layer:** 이 스트림에서 데이터를 수집하여 ETL(Extract, Transform, Load) 파이프라인을 구축하고, 이를 DB 스키마에 맞게 정규화하는 과정을 자동화합니다. (파이프라인의 안정성 확보가 핵심)
3.  **Metric Store 분리:** 실시간 추적 지표(Level 1)와 복잡한 행동 분석 지표(Level 2, 3)를 분리된 스토어에 저장하여 시스템의 응답성을 유지합니다.

#### 4. 최종 실행 액션 플랜
다음 단계는 이 로깅 방안을 실제 시스템에 반영하는 것입니다.

1.  **DB 스키마 확장:** Level 2 및 Level 3 요구사항을 반영하여 DB 스키마 변경(Migration) 계획을 수립합니다. (필요시 `schema_update` 명령 실행)
2.  **파이프라인 설계:** 이벤트 스트림 기반의 데이터 로깅 파이프라인의 상세 아키텍처를 문서화합니다.
